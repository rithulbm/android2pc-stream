# Security reviews

## Review 1 — before implementation

1. **Can an unpaired phone cause PC work?** The mobile service fails closed unless a Keystore-decrypted pairing record passes the same strict validator used at QR import. The PC independently validates its DPAPI record and requires the current SRT secret and secured AES-GCM key state before forwarding bounded TS groups to its private decoder child. Live adversarial verification still requires the matching installer and a physical phone.
2. **Can a local attacker read or replay media?** SRT 1.5.6 preview AEAD is mandatory: AES-256-GCM, cryptographic mode 2, TSBPD, enforced encryption, and `SRTO_PBKEYLEN=32`. The passphrase is 32 random bytes encoded as 43 base64url characters. Mode 1 CTR and plaintext are not production fallbacks. Both ends verify the negotiated mode/key state. The QR has a ten-minute import expiry and credentials have an explicit expiry. End-to-end adversarial replay remains a physical-network test.
3. **Can malformed input exhaust memory or crash?** QR input is capped at 2048 UTF-8 bytes; fields are allowlisted; duplicates, unknown versions, public/multicast/loopback endpoints, invalid UTF-8/escaping, oversized labels/secrets, and unsafe numbers are rejected. JNI repeats all bounds checks. Encoded samples, TS output, queue bytes, queue entries, and reconnect attempts are bounded.
4. **Can secrets leak?** QR text, passphrases, raw SRT URLs, media, local IPs, and packets are never logged. Endpoint secrets are AES-GCM encrypted with a non-exportable Android Keystore key. Android backup is disabled and no crash/analytics SDK is present. Native secret buffers are zeroed at stop. No browser code exists.
5. **Can the phone become public?** The native layer creates only an outbound SRT caller socket to a private IPv4 endpoint after Android 17's runtime `ACCESS_LOCAL_NETWORK` permission is granted. There is no listener, HTTP server, UPnP, NAT-PMP, PCP, router API, cloud endpoint, or broad hostname resolution.
6. **Are resources always released?** One service-owned session closes codecs, camera, microphone, surfaces, network callbacks, native socket/thread, notification, CPU wake lock, and Wi-Fi lock through idempotent terminal cleanup. Each partial startup step registers its cleanup before the next step.
7. **Can races silently restart capture?** Media failure callbacks are scoped to a monotonically increasing service session generation. Stop and quality reconfiguration invalidate the old generation before it can affect a replacement pipeline. Start/Stop commands are serialized and a start-request atomic gate rejects duplicate Start delivery. Cleanup is idempotent. The service is `START_NOT_STICKY`, and there is no boot receiver.

## Review 2 — handoff

Completed on 2026-08-16 after the clean release build.

1. **Source and logging boundary:** An authored-source scan found no `Log`, console output, stack-trace printing, analytics/telemetry SDK, browser/WebView, cloud URL, `srt_bind`, `srt_listen`, or `srt_accept` call. SRT applications and logging are disabled at CMake configuration, and the release native test seam is disabled. Vendored SRT contains receiver APIs because it is a general transport library, but the linked sender path invokes only socket creation, outbound `srt_connect`, send, option, status, and close operations.
2. **Manifest and platform exposure:** The built manifest has backup and cleartext traffic disabled. Pairing activity and streaming service are non-exported; the launcher activity is the sole intentionally exported component. There are no providers, broadcast receivers, boot hooks, or externally callable service intent filters. API 37 local-network permission, camera/microphone FGS types, notification permission, and required lock/network permissions are explicit.
3. **Secrets and JNI:** The pairing parser and the JNI bridge independently enforce length, canonical encoding, private-IPv4, port, expiry, latency, secret, codec, device-label, and sample-size bounds. Pairing records are encrypted as one AES-256-GCM value with a non-exportable Keystore key and fresh system-generated IV. JNI handles are registry-owned `shared_ptr` values rather than caller-controlled pointers. Java, JNI, and native temporary secret buffers are destroyed or zeroed on their terminal paths. No endpoint, secret, packet, QR payload, or media bytes enter status diagnostics. A sanitized model label is deliberately non-secret SRT handshake metadata; it is limited to 48 safe ASCII characters and is not a serial number, account, advertising ID, or other unique device identifier. The PC displays it only after the encrypted key states are secured.
4. **Transport fail-closed behavior:** The production socket is caller-only and restricted to canonical private IPv4. SRT 1.5.6 is configured for live sender/message mode, 1316-byte payloads, enforced encryption, 32-byte key material, and cryptographic mode 2. A connection is accepted only after negotiated mode 2 and both SRT key states report secured; plaintext and CTR downgrade are terminal failures. Queue entries/bytes, samples, TS groups, timeouts, reconnect attempts, and wake-lock duration are bounded.
5. **Lifecycle and failure behavior:** A single service-owned state machine gates pairing, permissions, explicit scan/button start, connect, stream, interruption, quality restart, reconnect, stop, and failure. A successful QR scan in the visible Activity is the user action that continues through any required permission prompts and starts the foreground service; it never bypasses Android permission grants. Session generations reject stale callbacks. Duplicate start/stop, partial startup, network loss, audio-focus loss, credential expiry, camera loss, congestion fallback, severe/critical thermal paths, and notification Stop all converge on idempotent cleanup. Producers close before native transport, then callbacks, CPU/Wi-Fi locks, foreground notification, and service state are released. `START_NOT_STICKY` prevents system resurrection.
6. **Automated evidence:** The clean gate passed 43 JVM tests with zero failures and 7 API 37 device tests. JVM coverage includes successful-scan auto-start decisions, safe bounded device labels, supported camera-size selection, aspect-preserving preview transforms, relative sensor/display rotation, front-camera mirroring, and sound-cue mappings. Device tests exercise real Android Keystore round trips and tamper rejection, built-manifest exposure, the release native queue/mux/config test seam in debug, microphone-on default UI, visible main-screen controls, and the scan-to-start regression with fail-closed handling when no usable camera/encoder configuration exists. Strict Android lint passed with warnings treated as errors. Both debug and minified release native builds passed for `arm64-v8a` and `x86_64`.
7. **APK and dependency evidence:** Release runtime dependencies are limited to Kotlin stdlib 2.2.10, JetBrains annotations 13.0, and ZXing core 3.5.4. The release APK contains only `liblocal_sender.so` and `libc++_shared.so` per ABI plus the declared notice asset; no analytics, network client, dynamic module, or test library is bundled. The root handoff APK is zip-aligned, verifies with APK Signature Scheme v3, installed successfully, and cold-launched on Android 17. Its development certificate is not a production trust identity and must be replaced for publication.
8. **Residual proof boundary:** The matching PC receiver and Windows native tests/build pass. The 0.2.0 installer was applied to the target machine: its per-user helper control pipe responded to an installed `/show-qr` client, OBS 32.2.1 discovered and restored the source without a registration error, and the OBS process bound the selected private address on UDP 9000. Emulator evidence still cannot prove real rear/front-camera optics, autofocus/exposure, physical-phone pairing/transport, microphone A/V sync, screen-off survival, hardware HEVC/4K60, OEM background policy, Wi-Fi roaming, thermal adaptation, battery drain, or a two-hour stream. Those are explicitly retained in `physical-device-validation.md`; none is described as passed.
